## FIX-003: Timestamp Format → Date/Time (UX-002)

### Current Behavior
```swift
// CravingListView.swift:91
Text(craving.timestamp, style: .relative)
// Shows: "55 min, 37 sec"

// UsageListView.swift:151
Text(usage.timestamp.formatted(date: .abbreviated, time: .shortened))
// Shows: "Jan 26, 2026 at 6:30 PM"
```

Note: UsageListView already uses the correct format. CravingListView uses `.relative` which shows awkward precision.

### Expected Behavior
Both should show: `"Today at 6:30 PM"` or `"Jan 26 at 6:30 PM"`

### Proposed Implementation

**Option A: Use same format as UsageListView (Simple)**
```swift
// CravingListView.swift:91
Text(craving.timestamp.formatted(date: .abbreviated, time: .shortened))
```

**Option B: Smart relative formatting (Better UX)**
Create a shared `TimestampFormatter` utility:

```swift
// Cravey/Presentation/Utilities/TimestampFormatter.swift
import Foundation

enum TimestampFormatter {
    /// Formats timestamp for list display
    /// - "Today at 6:30 PM" (same day)
    /// - "Yesterday at 3:00 PM" (yesterday)
    /// - "Jan 25 at 3:00 PM" (older)
    static func listDisplay(_ date: Date, relativeTo now: Date = Date()) -> String {
        let calendar = Calendar.current
        let timeFormatter = DateFormatter()
        timeFormatter.dateFormat = "h:mm a"
        let timeString = timeFormatter.string(from: date)

        if calendar.isDateInToday(date) {
            return "Today at \(timeString)"
        } else if calendar.isDateInYesterday(date) {
            return "Yesterday at \(timeString)"
        } else {
            let dateFormatter = DateFormatter()
            dateFormatter.dateFormat = "MMM d"
            return "\(dateFormatter.string(from: date)) at \(timeString)"
        }
    }
}
```

**Files to Modify:**
- Create: `Cravey/Presentation/Utilities/TimestampFormatter.swift`
- Modify: `Cravey/Presentation/Views/Craving/CravingListView.swift:91`
- Modify: `Cravey/Presentation/Views/Usage/UsageListView.swift:151` (optional, for consistency)

**Test Requirements:**
- Unit tests for TimestampFormatter with various dates
- Test "Today", "Yesterday", and older dates
- Test edge cases (midnight, year boundary)

### Recommendation
**Option B** - Better UX, more human-readable. Senior engineers prefer dedicated formatters over inline formatting.

## FIX-004: HomeView Sheet Success Race Condition (BUG-026)

### Current Behavior
```swift
// HomeView.swift:58-77
.sheet(isPresented: $showCravingLogSheet) {
    let didSucceed = cravingLogViewModel?.didSucceed ?? false  // ← Read AFTER nil check
    cravingLogViewModel = nil  // ← Set to nil
    // ...
    if didSucceed {  // ← May be false even when it should be true
        successMessage = "Craving logged"
        showSuccessToast = true
    }
}
```

The `onDismiss` closure reads `didSucceed` but the ViewModel may already be deallocated.

### Expected Behavior
Success state should be captured reliably before ViewModel is released.

### Proposed Implementation

**Option A: Capture before nil (Quick fix)**
```swift
.sheet(isPresented: $showCravingLogSheet) {
    // Capture success state FIRST
    let didSucceed = cravingLogViewModel?.didSucceed ?? false

    // THEN reset
    cravingLogViewModel = nil

    // Refresh and show toast
    Task { await cravingListViewModel.fetchCravings() }
    if didSucceed {
        successMessage = "Craving logged"
        showSuccessToast = true
    }
}
```

Wait - this IS the current code. The issue is that Swift's sheet onDismiss may be called at different times. Let me re-analyze...

**Option B: Use completion callback pattern (Robust)**
Add completion handler to ViewModel:

```swift
// CravingLogViewModel.swift
var onSuccess: (() -> Void)?

func logCraving() async {
    // ... existing logic ...
    if saved {
        didSucceed = true
        onSuccess?()  // Notify immediately on success
    }
}
```

```swift
// HomeView.swift
Button("Log Craving") {
```

## FIX-005: StartupFailure Alert Not Shown (BUG-025)

### Current Behavior
```swift
// CraveyApp.swift:34
} catch let error as DependencyContainer.StartupFailure {
    // ...
    _showStorageAlert = State(initialValue: false)  // ← Bug: should be true
}
```

When both persistent AND in-memory storage fail, `AppUnavailableView` is shown but no alert.

### Expected Behavior
Actually, looking more closely: when `StartupFailure` is thrown, the app shows `AppUnavailableView` which already displays the error. The `showStorageAlert` is for `InitializationError` (fallback mode), not `StartupFailure`.

### Analysis
This may NOT be a bug. Let me trace the logic:
1. `StartupFailure` → shows `AppUnavailableView` (full-screen error)
2. `InitializationError` → shows alert but app continues in fallback mode

The current behavior seems correct: when startup completely fails, show full-screen error. When only persistent fails but in-memory works, show alert warning.

### Recommendation
**NO CHANGE NEEDED** - Current behavior is correct. Update the audit doc to mark as "Not a Bug".

## FIX-008: Delete All Data Atomicity (BUG-029)

### Current Behavior
```swift
// SwiftDataDeleteAllUserDataUseCase.swift:16-30
// Step 1: Delete files (may fail)
try await Task.detached(...) { try FileStorageManager.deleteAllRecordings() }.value

// Step 2: Delete database (proceeds even if Step 1 failed)
try await MainActor.run { ... }
```

### Expected Behavior
Either all data is deleted, or none is (atomic operation).

### Proposed Implementation

**Option A: Collect errors, report all (Comprehensive)**
```swift
func execute() async throws {
    var errors: [Error] = []

    // Step 1: Try to delete files
    do {
        try await Task.detached(priority: .utility) {
            try FileStorageManager.deleteAllRecordings()
        }.value
    } catch {
        errors.append(error)
    }

    // Step 2: Delete database records
    do {
        try await MainActor.run {
            try modelContext.delete(model: CravingModel.self)
            try modelContext.delete(model: UsageModel.self)
            try modelContext.delete(model: RecordingModel.self)
            try modelContext.delete(model: MotivationalMessageModel.self)
            try modelContext.save()
        }
    } catch {
        errors.append(error)
    }

    // Report if any errors occurred
    if !errors.isEmpty {
        throw DeleteError.partialFailure(errors)
    }
}
```

**Option B: Delete database first, then files (Safer order)**
Database records point to files. If we delete files first and database fails, we have dangling references. If we delete database first and files fail, we have orphaned files (less bad - just wasted space).

```swift
func execute() async throws {
    // Step 1: Delete database records FIRST
    try await MainActor.run {
        try modelContext.delete(model: CravingModel.self)
        // ...
        try modelContext.save()
    }

    // Step 2: Delete files (best effort - log but don't throw)
    do {
        try await Task.detached(priority: .utility) {
            try FileStorageManager.deleteAllRecordings()
        }.value
    } catch {
        logger.warning("Failed to delete recording files: \(error.localizedDescription)")
        // Don't throw - database is already clean
    }
}
```

**Files to Modify:**
- `Cravey/Data/UseCases/SwiftDataDeleteAllUserDataUseCase.swift`

**Test Requirements:**
- Test successful deletion of both
- Test database deletion succeeds, file deletion fails → success with warning
- Test database deletion fails → throws, files NOT deleted

### Recommendation
**Option B** - Prioritize database integrity. Orphaned files are annoying but not data corruption.

## FIX-009: Duplicate Timestamp Warning Logic (QUALITY-015)

### Current Behavior
Both `CravingLogViewModel` and `UsageLogViewModel` have identical:
```swift
var isTimestampOld: Bool {
    guard let sevenDaysAgo = Calendar.current.date(byAdding: .day, value: -7, to: Date()) else {
        return false
    }
    return timestamp < sevenDaysAgo
}
```

### Expected Behavior
Shared utility to avoid duplication.

### Proposed Implementation

```swift
// Cravey/Presentation/Utilities/TimestampValidation.swift
import Foundation

enum TimestampValidation {
    static let oldThresholdDays = 7

    /// Returns true if timestamp is older than threshold (default 7 days)
    static func isOld(_ timestamp: Date, threshold: Int = oldThresholdDays, relativeTo now: Date = Date()) -> Bool {
        guard let thresholdDate = Calendar.current.date(byAdding: .day, value: -threshold, to: now) else {
            return false
        }
        return timestamp < thresholdDate
    }
}
```

Then in ViewModels:
```swift
var isTimestampOld: Bool {
    TimestampValidation.isOld(timestamp)
}
```

**Files to Modify:**
- Create: `Cravey/Presentation/Utilities/TimestampValidation.swift`
- Modify: `Cravey/Presentation/ViewModels/CravingLogViewModel.swift`
- Modify: `Cravey/Presentation/ViewModels/UsageLogViewModel.swift`

**Test Requirements:**
- Unit test TimestampValidation with various dates
- Test 6 days old → false
- Test 7 days old → true
- Test 8 days old → true
