# BUG-033: “Current Location” can error/timeout before user responds to permission prompt

**Priority:** P2 (Edge case / UX reliability)
**Status:** OPEN
**Reported:** 2026-01-30
**Primary Area:** Location (CoreLocation)

## Problem

When the user taps **📍 Current** for the first time (authorization status `.notDetermined`), `LocationService` polls authorization with a fixed sleep/retry loop. If the user takes longer than the retry budget to respond to the iOS permission prompt, the request can return an error like:

- `"Location permission not determined after retries"`

This produces a confusing UX: the user may grant permission but still needs to tap **📍 Current** again to actually fetch GPS coordinates.

## Location

- `Cravey/Data/Services/LocationService.swift` (authorization polling + retry logic)
  - `requestCurrentLocationWithRetry` (lines ~27–62)

## Steps To Reproduce

1. Fresh install (or reset location permission for Cravey).
2. Open `CravingLogForm` or `UsageLogForm`.
3. Tap **Location → 📍 Current**.
4. When the system permission prompt appears, wait ~6+ seconds before choosing Allow/Don’t Allow.
5. Observe the UI shows an error and clears selection.
6. Even after choosing “Allow While Using App”, location is not captured until the user taps **📍 Current** again.

## Expected

- The first tap should either:
  - wait for the authorization prompt to be resolved (within a reasonable timeout), then fetch location, or
  - clearly report “Permission not granted yet” without treating it as an error and without forcing a second tap.

## Actual

- The request can “give up” while the permission prompt is still pending and return `.error(...)`.
- The user must retry by tapping **📍 Current** again after granting permission.

## Root Cause (Likely)

- Authorization handling is implemented as a retry loop:
  - `requestWhenInUseAuthorization()`
  - `Task.sleep(500ms)`
  - recurse until retries exhausted

This is time-based polling rather than awaiting an authorization change signal.

## Proposed Fix

- Replace polling with a true “await authorization change” mechanism:
  - Bridge `CLLocationManagerDelegate` authorization callbacks into an `AsyncStream`, or
  - Use any iOS 17+/18 async authorization updates API if available (preferred if it exists).
- Ensure cancellation is handled distinctly from timeout (don’t map `CancellationError` to `.timeout`).
- Keep a single timeout budget for the overall “authorize + fetch” request.

## Acceptance Criteria

- [ ] First-tap **📍 Current** works reliably after granting permission (no second tap needed).
- [ ] No repeated `requestWhenInUseAuthorization()` calls.
- [ ] Cancellation does not surface as “timeout”.
- [ ] SwiftLint warnings for `LocationService` complexity/body length are resolved as part of refactor (or explicitly waived with justification).
